# 股票组合智能分析客户端：开发设计

日期：2026-10-15。状态：用户已于本会话批准“按这份设计分阶段开发”。该设计采用分阶段交付，不代表应用已经实现。

## 1. 用户目标与验收含义

用户要求先审阅需求与架构，再完成开发；项目必须独立存放，代码具有高可读性和可维护性，并支持上传 GitHub 作为项目输出。用户已经授权开发与独立项目目录。

原PRD是包含124条FR的完整平台愿景，本设计保留该目标，按可验收的纵向闭环推进。首个可运行交付称为 M0，不将演示页面、静态假数据或接口占位称作完整产品。M1–M3 的各项需求保留独立验收状态。缺行情授权、模型API或券商凭证时，相关能力标为未配置/待接入，不伪装成功。

工作假设：优先个人本地研究、A股日线；界面中文，Windows优先；默认不联网、不发送个人持仓；行业分类由导入元数据提供并固定版本。正式交易所日历由用户导入或授权provider提供，合成日历只用于演示，不能冒充真实节假日。

## 2. 选定架构与备选

推荐模块化单体，保留原文领域划分，先确保数据→选股→组合→回测→模拟账本→报告可运行。完整微服务方案增加数据库、部署与一致性成本，目前没有需要它的负载证据；闭环完成后可先独立重任务worker，再依据实际瓶颈拆服务。

前端使用 SvelteKit 2 + Svelte 5 + TypeScript strict，静态SPA构建，可在浏览器开发与Tauri2桌面壳复用。后端 FastAPI + Pydantic2，SQLite本地持久化，领域层独立于ORM；后续服务部署迁移PostgreSQL。数据文件原文/导入批次与数据库元数据分开，使用内容摘要固定版本。

浏览器开发版和Windows安装包分别验收。Tauri正式包管理后端sidecar，绑定127.0.0.1，启动时建立会话令牌并健康探测，退出时结束自己的子进程；不依赖用户机器上固定Python路径。安装包必须在Rust/MSVC/WebView2工具链与CI构建后测试，不能只交配置文件。

## 3. 工程结构与依赖方向

```text
stock-portfolio-client/
  apps/
    api/
      src/portfolio_client/
        api/              # 路由、DTO、错误映射
        application/      # 用例、事务、任务编排
        domain/
          market/         # 标的、交易日历、时间语义
          screening/      # 条件DSL、评分、筛选归因
          portfolio/      # 约束、权重、调仓
          accounting/     # 账本、公司行为、成本
          execution/      # 订单状态机与风控
          research/       # 回测、指标、报告证据
        infrastructure/   # SQLite、文件、provider、LLM适配
      tests/
    client/
      src/lib/features/   # 每个业务功能的组件与状态
      src/lib/components/ # 基础组件和图表
      src/lib/api/        # 生成类型与统一客户端
      src/routes/         # 页面编排
      src-tauri/          # 桌面生命周期与最小权限
  contracts/              # OpenAPI与版本化DSL
  samples/                # 明确标识的合成数据和导入示例
  scripts/                # 项目内启动、检查、打包
  docs/                   # PRD、设计、验收证据
  .github/workflows/      # CI与后续发布
```

`api → application → domain`；infrastructure实现domain定义的协议，通过组合根注入。domain不得依赖Web、数据库、厂商SDK；同一领域内核供回测与模拟盘调用。模块间传明确类型，不传裸SQL或随意字典。页面不直接计算费用/收益、不直连模型厂商。

公开接口有类型，函数/组件保持单一责任；代码增长导致难以独立解释时按职责拆分，避免为凑行数机械拆文件。新增provider、优化器和LLM实现不修改核心业务流程。只保留一种主要实现路径，避免一功能同时依赖多套同类框架。

## 6. 数据、时间与账本

内部标的键为security_id，包含交易所映射；金额Decimal、数量整数（扩展资产类型时单独定义），JSON金额字符串，配置和返回对象带单位。日线包含原始OHLC、成交量/额、数据来源、版本、披露可用时间与导入时间；缺失值不填0。

以交易日历和明示as_of推进。M0日线资料可进行历史研究，但若源文件没有修订历史，不对财务PIT作虚假保证。public_pit用于公开历史，system_replay还约束当时入库时间。任何结果记录数据/策略/费用/日历版本与seed；后续状态、行业和指数成分同样按时点还原。

回测和模拟盘：先处理当日公司行为和到期结算，再处理以前已提交且当日可执行的订单；成交按当时可知信息限制；随后按收盘原始价估值，再生成下一交易日信号。买入股票当日不可卖；卖出资金可买与可取分开。日线缺少盘口，只能提供有明确假设的撮合。

每个成交同时追加现金、费用、股数和审计事件，数据库事务提交；异常全回滚。分红应收与现金支付分开，退市不产生虚构卖出。数据导入为预检→确认→批次事务提交，禁止校验一半就覆盖有效数据。

周/月/年策略在该周期最后一个交易日收盘产生信号，下一交易日执行；日策略每个交易日收盘产生信号。首个建仓时点至少已有完整指标窗口；不足窗口返回具体原因。基准使用同区间与交易日对齐，标明价格/全收益口径与无风险利率年化因子。

## 7. API与任务契约

API以 `/v1` 开头，统一成功data/meta、失败error(code,message,details,trace_id)；分页、as_of、data_version明确。OpenAPI是类型来源，前端生成类型并在CI检查漂移。

主要资源：health/config、datasets/imports/calendar、securities/quotes/search、screening/presets、portfolios/holdings/optimizations、risk、backtests、paper/accounts/orders/trades、reports、ai/runs。长任务POST返回202与task_id，GET查询持久化状态；cancel是幂等请求，不保证已完成任务回滚。

所有金融写操作需Idempotency-Key和规范化载荷摘要；同账户同操作同键异内容409。资金冻结、订单、账本与审计原子提交。状态机阻止非法跳转，外部执行状态未知时显示unknown并对账，不悄悄重发。

流式AI事件包含run_id、seq、type、version。POST通过fetch消费SSE，断线按run_id查询或seq恢复；取消请求独立于断开UI连接。没有可恢复事件历史时明确返回过期状态，不能把重新生成当续写。

## 8. 客户端设计

界面采用中文金融工作台：左侧固定导航，顶部数据环境/截至时间/搜索，主区按研究流程组织。默认深色，克制的蓝色操作强调，A股默认红涨绿跌并可切换；颜色不是唯一状态线索。图表标注单位、基准、数据类型与截至时间。

页面包括总览、数据中心、行情、选股、组合、回测、风险、模拟盘、报告与设置。图表和表格联动；数字能查看来源与口径。所有按钮连接真实API或明确的本地编辑操作；不可用能力显示条件和原因。避免用占位的模型胜率或伪实时数字填满驾驶舱。

AI抽屉显示工具结果、引用、执行进度与取消；AI生成数据与确定性指标分开标记。可访问性包括键盘导航、可见焦点、表格语义、对比度和reduced-motion。列表和图表量大时分页/降采样，避免海量点和全局响应式更新拖慢交互。

## 9. 安全与错误恢复

单用户本地模式只绑定loopback，仍校验令牌、Host/Origin和受控CORS；文件导入限制大小、扩展名、编码与目标目录。模型URL由受控配置设置，非来自外部网页。日志和导出不含密钥；配置检查失败应清楚说明字段问题。

AI只产结构化研究建议，执行端只接受服务端校验后的白名单DSL/工具；生成SQL不直接执行。危险交易确认绑定摘要与有效期，再验资金、行情和风控。紧急停止立即禁新单，恢复才二次确认；离线订单不自动发送。

UI离线显示缓存时间；网络失败只对幂等操作按规则重试。任务失败保留进度和错误证据，重启恢复queued任务或明确终止running任务。数据库迁移有版本、备份和恢复指引，不能只写“可回滚”而不测试。

## 10. 测试与维护性验收

1. 领域测试覆盖费用基数/最低佣金、资金守恒、整股、T+1、分红支付、未来数据与退市；使用独立预期值，不照抄实现公式制造测试。
2. 回测与模拟用相同输入事件比对逐笔账本；历史数据生成器有固定seed和极端场景，合成数据不作为策略有效性证据。
3. 集成测试覆盖导入事务、同键异载荷409、并发重复请求、取消/暂停、重启持久化、错误输入与权限边界。
4. 前端运行strict检查、组件交互测试与构建；端到端覆盖导入→筛选→建组合→回测→模拟盘→报告，检查空态和失败态。
5. 性能测试声明机器、数据规模与冷热状态；M0目标为200标的×3年日线筛选/指标交互可用，后续扩大到全市场后单独验证SLO。
6. Python格式、Ruff、类型检查与依赖边界检查；TypeScript/Svelte、ESLint/Prettier；OpenAPI生成检查。锁定依赖，不引入不可解释的大型框架。
7. 提交前检查真实密钥和个人数据排除；CI分别记录后端测试、前端检查/构建与Windows包构建状态。
